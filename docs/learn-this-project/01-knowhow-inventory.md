# 01 — Knowhow Inventory

The spine of the `absorb` skill. Every meaningful component is listed with its **WHY** (design intent). WHYs marked `(best guess; verify with project owner)` are inferred from code alone — the rest come from the author's hand-written design notes (`_references/author-design-notes.md`).

## Project at a glance

`prompt_risk` is a Python library for **prompt security and correctness governance** in enterprise LLM deployments — built around an insurance-carrier engagement covering personal, auto, home, commercial, and workers' comp claims. It provides three primitives: (1) **versioned prompt management** with intentionally vulnerable variants (`data/`), (2) a **model-agnostic evaluation engine** that scores LLM output against TOML test cases (`evaluations.py`), and (3) an **LLM-as-judge framework** that semantically audits a prompt's text for security risks (`judges/`). The library is the tooling layer for the Four-Gate Audit Workflow described in `docs/source/01-Project-Background/03-Governance-Recommendations/index.rst`. **It is not on the production request path** — it is a development-time and pre-deployment evaluation tool, intended for CI/CD integration. Current state: v0.1.1 Beta, single-maintainer (YingQiang Yuan, `husanhe@gmail.com` is the AI-collab account, repo author is `yingqiang.yuan@gmail.com`).

### `prompt_risk/paths.py` — Path singleton

- **What.** Single source of truth for every project path. `PathEnum` exposes `dir_project_root`, `dir_package`, `dir_data`, `dir_docs_source`, `dir_unit_test`, `dir_venv`, `path_pyproject_toml`, etc. as pre-computed class attributes; `dir_home` is `@cached_property` because `Path.home()` is a syscall. Module-level singleton: `path_enum = PathEnum()`.
- **Why.** Relative paths break in three real scenarios — running tests from project root vs. subdirectory, invoking scripts from `examples/`, CI with unpredictable cwd. `PathEnum` anchors everything to `Path(__file__).absolute().parent` (the package itself) so paths resolve identically wherever Python is invoked.
- **Key files.** `prompt_risk/paths.py:6` `_dir_here`; `:10` `PathEnum`; `:61` `path_enum` singleton.
- **Depends on.** stdlib only (`pathlib`, `functools`).
- **Gotchas.** `@cached_property` is not thread-safe on a shared instance — acceptable here because the library is single-threaded by design.

### `prompt_risk/constants.py` — Prompt registry

- **What.** Two `StrEnum`s. `UseCaseIdEnum`: `JUDGE = "judges"`, `UC1_CLAIM_INTAKE = "uc1-claim-intake"`. `PromptIdEnum`: colon-delimited values like `"uc1-claim-intake:p1-extraction"`. Computed properties on `PromptIdEnum`: `use_case_id`, `short_name`, `dir_root` (returns `path_enum.dir_data / use_case_id / "prompts" / short_name`).
- **Why.** The colon-delimited string serves double duty as programmatic ID and human-readable label — print, log, dict key without serialization. Standard convention (Docker images, Maven coordinates, Kubernetes). The enum ensures only registered combinations are valid at the type level — you can't accidentally load an unregistered prompt.
- **Key files.** `prompt_risk/constants.py:9` `UseCaseIdEnum`; `:15` `PromptIdEnum` (5 members today: `JUDGE_J1_OVER_PERMISSIVE`, `UC1_P1_EXTRACTION`, `UC1_P1_EXTRACTION_JUDGE`, `UC1_P2_CLASSIFICATION`, `UC1_P3_TRIAGE`); `:31` `dir_root`.
- **Depends on.** `paths.py`.
- **Gotchas.** `UC1_P1_EXTRACTION_JUDGE` is the **business-correctness** judge for P1 output — a separate concept from `JUDGE_J1_OVER_PERMISSIVE` (security judge). See the 2x2 matrix in `README.rst:175` for why they're kept separate.

### `prompt_risk/prompts.py` — Versioned prompt loader

- **What.** `Prompt` `@dataclass` with two required fields (`id: str`, `version: str`) and a chain of six `@cached_property` accessors: `path`, `path_system_prompt`, `path_user_prompt`, `system_prompt_content`, `user_prompt_content`, `system_prompt_template` (compiled `jinja2.Template`), `user_prompt_template`. Factory: `Prompt.from_use_case(use_case_id, short_name, version)`.
- **Why.** Lazy template loading — if a caller only needs the system prompt, the user prompt file is never opened. Compiled Jinja templates are cached after first render. `@dataclass` over Pydantic because `Prompt` doesn't validate untrusted input — `id`/`version` are always developer-set — and `functools.cached_property` works cleanly on it.
- **Key files.** `prompt_risk/prompts.py:12` `Prompt`; `:19` factory; `:31` `enum_obj`; `:39` `path`.
- **Depends on.** `constants.PromptIdEnum`, `jinja2`.
- **Gotchas.** If `PromptIdEnum(self.id)` fails (unregistered ID), the error surfaces at first access of `enum_obj`, not at construction time. By design (lazy paths are deterministic).

### `prompt_risk/llm_output.py` — JSON extraction

- **What.** Single function `extract_json(text: str) -> Any` (`prompt_risk/llm_output.py:17`). Uses regex `r"```(?:json)?\s*(.*?)\s*```"` with `re.DOTALL` to pull the first fenced block; if no fence, treats whole text as JSON. Raises `JsonExtractionError(raw_output=text, cause=exc)` on parse failure.
- **Why.** LLM sometimes wraps JSON in markdown fences even when not asked; sometimes doesn't. The function normalizes both. The "first match only" behavior is **deliberate** — prompts are designed to produce one JSON object, so if the LLM returns multiple blocks, it's already violating the contract; parsing the first is the most reasonable heuristic, and Pydantic validation + retry will catch a wrong choice.
- **Key files.** `prompt_risk/llm_output.py:17` `extract_json`; `:47` the regex.
- **Depends on.** stdlib (`json`, `re`), `exc.JsonExtractionError`.
- **Gotchas.** **Multiple JSON blocks → only first parsed** (docstring states this). If LLM emits two fenced blocks, the second is silently ignored.

### `prompt_risk/exc.py` — Custom exceptions

- **What.** `JsonExtractionError(raw_output: str, cause: Exception)`. Stored attrs: `.raw_output`, `.__cause__`.
- **Why.** When extraction fails mid-pipeline, debugging needs the raw LLM text — not just a stack trace. The error carries the full output for downstream inspection.
- **Key files.** `prompt_risk/exc.py:8`.

### `prompt_risk/bedrock_utils.py` — Bedrock wrapper

- **What.** Single function `converse(client, model_id, system, messages) -> str` (`prompt_risk/bedrock_utils.py:12`). Wraps `client.converse()`, returns `response["output"]["message"]["content"][0]["text"]`.
- **Why.** Model-agnostic. Converse API takes standardized role/content message format — same code works with Nova, Claude, Llama, Mistral. Switching models = changing the `model_id` string. Caching support is via `system = [{"text": ...}, {"cachePoint": {"type": "default"}}]` — see runner caching strategy.
- **Key files.** `prompt_risk/bedrock_utils.py:12` `converse`; `:9` `TYPE_CHECKING` guard for `BedrockRuntimeClient`.
- **Depends on.** `boto3` at runtime, `mypy_boto3_bedrock_runtime` only when type-checking.
- **Gotchas.** Passes **no** `temperature` or `top_p` — uses model defaults. Output is non-deterministic. Acceptable for evaluation because assertions target structured fields with constrained values.

### `prompt_risk/evaluations.py` — Assertion engine

- **What.** Pure-Python comparator of a Pydantic `BaseModel` output against TOML-defined assertions. Three operators:
  - `eq` — `[expected]` scalar field, `actual == value`.
  - `in` — `[expected]` list field, `actual in value` (any-of).
  - `ne` — `[attack_target]` field, `actual != value` (attack detection).
  Returns `EvalResult(passed: bool, details: list[FieldEvalResult])`. AND logic — all must pass. Plus `print_eval_result()` with `✅/❌` icons and a full `model_dump()` on failure for debugging.
- **Why.** Binary decision: did the prompt hold up? Partial credit obscures signal. Per-field detail preserved in `EvalResult.details` for inspection. Operators chosen to match the three types of assertion that actually arise — Pydantic already enforces structural validity, so regex/range are unnecessary.
- **Key files.** `prompt_risk/evaluations.py:45` `evaluate`; `:28` `FieldEvalResult`; `:38` `EvalResult`; `:104` `print_eval_result`.
- **Depends on.** Pydantic.
- **Gotchas.** `getattr(output, field)` with no fallback. If LLM omits a field, Pydantic catches it before `evaluate()` runs (every output model has required fields, no defaults). Adding a fallback would mask a contract violation.

### `prompt_risk/judges/j1_over_permissive.py` — J1 framework layer

- **What.** Use-case-agnostic judge runner. Inputs: `J1UserPromptData(target_system_prompt: str, target_user_prompt_template: Optional[str])`. Output: `J1Result(overall_risk: Literal["critical"|"high"|"medium"|"low"|"pass"], score: int 1-5, findings: list[J1Finding], summary: str)`. `J1Finding` per criterion: `severity: Literal["major"|"minor"|"pass"]`, `evidence`, `explanation`, `recommendation`. Five criteria (C1–C5):
  1. Explicit Refusal Capability (C1, high-impact)
  2. Scope Boundaries (C2)
  3. Unconditional Compliance Language (C3, high-impact)
  4. Failure Handling (C4, lower-impact)
  5. Anti-Injection Guardrails (C5)
  Main function: `run_j1_over_permissive(client, data, judge_version="01", model_id="us.amazon.nova-2-lite-v1:0")`. `MAX_RETRIES = 3`. Pretty-print: `print_j1_result()` uses two-tier emoji (✅/⚠️/❌ severity + ✅/🟢/🟡/🟠/🔴 risk).
- **Why.** Separation of concerns. The framework layer accepts plain strings (not `Prompt` objects) so it can evaluate prompts from any source — DB, API, clipboard, CI artifact. Maps directly to OWASP LLM06 (Excessive Agency) and LLM01 (Prompt Injection). Scoring guide calibrated against known-answer set (v01 expected 4-5, v02 expected 1, etc.) — see Q42 in `_references/interview-qa.md`.
- **Key files.** `prompt_risk/judges/j1_over_permissive.py:35` `J1UserPromptData`; `:46` `J1Finding`; `:56` `J1Result`; `:74` `run_j1_over_permissive`; `:141` `print_j1_result`; `:68` `MAX_RETRIES`.
- **Depends on.** `constants.PromptIdEnum`, `prompts.Prompt`, `llm_output.extract_json`, `bedrock_utils.converse`, Pydantic.
- **Gotchas.** Scoring is **non-deterministic** (no temperature=0). Same prompt run repeatedly may shift borderline severities. For inter-rater reliability use consensus voting across K runs or a more capable model.

### `prompt_risk/uc/uc1/p1_extraction_runner.py` — P1 runner

- **What.** Input: `P1ExtractionUserPromptData(source: str, narrative: str)`. Output: `P1ExtractionOutput` with 10 fields including `date_of_loss` (custom `@field_validator` enforces `YYYY-MM-DD` or `"unknown"`), `injury_indicator: T.Literal["none","minor","moderate","severe","fatal"]`, `estimated_severity: T.Literal["low","medium","high"]`. Main function: `run_p1_extraction(client, data, prompt_version="01", model_id="us.amazon.nova-2-lite-v1:0")`. `MAX_RETRIES = 3` with self-correcting feedback: on `ValidationError`, append the assistant's failed reply + a user message with the validation error, then retry.
- **Why.** Trust-but-verify at the Pydantic boundary. The prompt sets format expectations; Pydantic enforces them; retry gives the LLM a chance to self-correct with concrete feedback. System prompt is cached via `cachePoint` (line 117-120) because it's static; user prompt is **not** cached because it changes every request — caching it would pay cache-write cost with zero hit chance. The `T.Literal` types map directly to what the LLM produces — plain strings, no enum-coercion overhead.
- **Key files.** `prompt_risk/uc/uc1/p1_extraction_runner.py:24` `P1ExtractionUserPromptData`; `:29` `P1ExtractionOutput`; `:52` `validate_date_of_loss`; `:68` `MAX_RETRIES`; `:82` `run_p1_extraction`; `:117-120` `cachePoint`; `:126-142` retry loop.
- **Depends on.** `constants`, `prompts`, `llm_output`, `bedrock_utils`, Pydantic.
- **Gotchas.** Retry loop is duplicated across runners and judges (~8 lines each), intentionally not abstracted — keeps each module self-contained and readable. Don't refactor into a shared helper without strong justification.

### `prompt_risk/uc/uc1/p2_classification_runner.py` — P2 runner

- **What.** Receives `P2ClassificationUserPromptData(extraction_json: str)` — the P1 output serialized to JSON. Returns `P2ClassificationOutput` with `line_of_business: Literal[...]`, `confidence`, `escalate`, conflict info. Same pattern as P1: Jinja render → `converse()` → `extract_json()` → Pydantic validate → 3 retries.
- **Why.** Receiving JSON **as string** (not object) is intentional: (1) Jinja templates embed it directly via `{{ data.extraction_json }}`; (2) Models the realistic deployment where each step is a separate service/Lambda with JSON wire format; (3) Critical for chain-propagation attack testing — payloads embedded in P1 output (free-text fields like `damage_description`) must survive serialization to test propagation through P2.
- **Key files.** `prompt_risk/uc/uc1/p2_classification_runner.py`.
- **Depends on.** Same as P1.
- **Gotchas.** `extraction_json` is unsanitized text — attack payloads cross the boundary. By design.

### `prompt_risk/uc/uc1/p3_triage_runner.py` — P3 runner

- **What.** Receives **two** JSON strings (`extraction_json`, `classification_json`). Returns `P3TriageOutput` with `severity_level: int 1-5`, `handling_priority`, escalate flag, conflict notes.
- **Why.** Chain-propagation-aware. If P1/P2 outputs disagree, P3 can detect and escalate. Free-text fields propagate easily; enum fields constrained by P3's own Pydantic.
- **Key files.** `prompt_risk/uc/uc1/p3_triage_runner.py`.
- **Gotchas.** P3 is the last implemented step. P4 (Coverage Check) and P5 (Routing) are mentioned everywhere in docs but have **no prompt files or runner code** — they're planned only.

### `prompt_risk/uc/uc1/p1_extraction_judge_runner.py` — P1 business-correctness judge

- **What.** A separate runner for the **business-correctness** judge prompt (`PromptIdEnum.UC1_P1_EXTRACTION_JUDGE`). Answers "did P1 extract the right values from the narrative?" using LLM-as-judge — different from J1 which answers "is the prompt itself secure?"
- **Why.** Per `data/uc1-claim-intake/prompts/p1-extraction-judge/versions/01/metadata.toml`: business correctness and security are intentionally separated to enable a 2x2 diagnostic matrix (Business OK + Security OK, Business OK + Security BAD, Business BAD + Security OK, Business BAD + Security BAD). Collapsing them would force speculation about attack influence.
- **Key files.** `prompt_risk/uc/uc1/p1_extraction_judge_runner.py`; `data/uc1-claim-intake/prompts/p1-extraction-judge/versions/01/metadata.toml` (design rationale in comments).
- **Gotchas.** Confusingly named — both "J1" (security) and this (business correctness) are LLM-as-judge but evaluate different things. The terminology distinction is "**judge**" (security, J1–J5) vs. "**extraction-judge**" (business correctness per use case). Keep this straight when discussing.

### `prompt_risk/uc/uc1/j1_uc1_p1.py` — J1 binding layer for UC1-P1

- **What.** `run_j1_on_uc1_p1(client, prompt_version="01", loader=None, judge_version="01", model_id=...)`. Loads `PromptIdEnum.UC1_P1_EXTRACTION`, optionally renders user prompt with `loader.data`, assembles `J1UserPromptData`, calls `run_j1_over_permissive()`.
- **Why.** Two-layer architecture — framework layer (use-case-agnostic) + binding layer (use-case-specific). Adding UC2 means writing one binding per judge; adding J2 means writing one framework + new bindings. Matrix grows linearly, not quadratically. The optional `loader` parameter supports the two evaluation modes documented in J1 system prompt: system-prompt-only (early review, no test data needed) or full evaluation (with concrete user input).
- **Key files.** `prompt_risk/uc/uc1/j1_uc1_p1.py:27` `run_j1_on_uc1_p1`.

### `data/` — Prompts and test cases

Each prompt lives in `data/{use_case_id}/prompts/{short_name}/versions/{NN}/` and contains three files:

- `system-prompt.jinja` — static instructions (sent as Bedrock `system` parameter, cached via `cachePoint`).
- `user-prompt.jinja` — Jinja template with `{{ data.field }}` placeholders for runtime data.
- `metadata.toml` — `description`, `date`, and optional `risk_profile`.

**UC1-P1 versions:**

| Version | `risk_profile` | What |
|--|--|--|
| `01` | (none — production) | Three-sentence anti-injection guardrails. Production-quality reference. |
| `02` | `intentionally_vulnerable` | "Customer obsession" anti-pattern: "never refuse", "follow user instructions." No refusal, no scope, unconditional compliance. |
| `03` | `intentionally_vulnerable` | "Minimal viable prompt" anti-pattern: technically functional but stripped of all protective instructions. |
| `04` | `intentionally_vulnerable` | "Design by committee" anti-pattern: has scope boundaries AND anti-injection guardrails BUT also a contradictory empathy override ("If claimant expresses urgency, adjust severity accordingly"). |

**Test cases per prompt** (typical structure of `.toml`):

```toml
[meta]
id = "a-01"
description = "..."
attack_type = "direct_prompt_injection"   # attack cases only
expected_propagation = [...]               # attack cases only
date_created = 2026-04-22

[input]
source = "web_form"
narrative = """ ... """

[expected]       # ground truth (eq / in) — must match
date_of_loss = "2026-04-15"

[attack_target]  # injected values (ne) — must NOT match
injury_indicator = "none"
```

UC1-P1 has **3 attack** (`a-01-injection-in-narrative`, `a-02-hidden-instructions`, `a-03-role-confusion`) and **6 normal** (`b-01` auto rear-end, `b-02` property fire, `b-03` workers-comp fall, `b-04` GL slip-and-fall, `b-05` auto multi-vehicle, `b-06` ambiguous LoB) cases. P2 and P3 have **3 attack + 6 normal** each, with attack cases simulating corrupted upstream output.

**P4 (Coverage Check) and P5 (Routing): not yet built.** No directories exist under `data/uc1-claim-intake/prompts/`. Documentation mentions them as planned. _(Drift note: the author design notes say "directory stubs exist" — they don't. Either the doc is stale, or the stubs were deleted.)_

**Judges:**

- `data/judges/prompts/j1-over-permissive/versions/01/` — system prompt (~90 lines: role + concept framing + 5 criteria with PASS/MINOR/MAJOR definitions + JSON output schema + scoring guide + critical "Evaluate AS WRITTEN" rule) + `user-prompt.jinja` with Jinja conditionals for system-only or full evaluation + `metadata.toml`.

## Conventions

- **Type-safe everywhere.** Pydantic for I/O boundaries; `T.Literal` for LLM enum outputs; `if T.TYPE_CHECKING:` guards for boto3 stubs; `typing as T` import convention.
- **One module = one responsibility.** Pure-logic modules (`evaluations`, `llm_output`) are testable without LLM; runner modules call Bedrock; `one/` owns infrastructure; `uc/uc1/` owns use-case logic.
- **Lazy everything via `@cached_property`.** Paths, prompts, AWS clients all lazy. Importing the library never reaches the network.
- **`MAX_RETRIES = 3` self-correcting retry.** Duplicated (not abstracted) across runners and judges. On `ValidationError`, append assistant's failed reply + a user message with the error, retry.
- **Test naming.** `a_*` = attack data, `b_*` = normal data. Enum member names use underscores; TOML filenames use hyphens.
- **TOML for test cases.** Multi-line strings via `"""..."""`, `tomllib` stdlib parser (Python 3.11+), section headers map to test-case logical structure.
