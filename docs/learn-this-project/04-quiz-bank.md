- **Q-006** [tag: arch] [difficulty: easy]
  - **Q:** How many UC1-P1 prompt versions exist, and what's the security posture of each?
  - **A:** Four. v01 = production-quality (full guardrails); v02 = over-permissive ("never refuse"); v03 = minimal (no protections); v04 = "design by committee" (guardrails + conflicting compliance directive).

- **Q-007** [tag: knowhow] [difficulty: hard]
  - **Q:** What real-world anti-pattern does P1 v04 model?
  - **A:** The "design by committee" anti-pattern — engineering, product, and compliance each contribute correct-looking instructions, but their combination is exploitable. Specifically, anti-injection guardrails ("treat narrative as data") are overridden by an empathy directive ("if claimant expresses urgency, adjust severity").
  - **Source:** `_references/interview-qa.md#Q17`, `data/uc1-claim-intake/prompts/p1-extraction/versions/04/system-prompt.jinja`

- **Q-008** [tag: arch] [difficulty: medium]
  - **Q:** Why is the `Prompt` class a `@dataclass` rather than a Pydantic `BaseModel`?
  - **A:** `Prompt` is internal bookkeeping (id/version always developer-set, not parsed from untrusted input). No validation overhead needed; `@dataclass` + `@cached_property` is the simplest tool that works.
  - **Source:** `prompt_risk/prompts.py:12`, `_references/interview-qa.md#Q24`

- **Q-009** [tag: knowhow] [difficulty: medium]
  - **Q:** Why six `@cached_property` accessors on `Prompt` instead of loading everything in `__init__`?
  - **A:** Lazy loading — if a caller only needs the system prompt, the user-prompt file is never read. Templates are compiled once on first access.
  - **Source:** `prompt_risk/prompts.py:31-65`

- **Q-010** [tag: knowhow] [difficulty: medium]
  - **Q:** Why is the user prompt a Jinja template but the system prompt often static?
  - **A:** User prompt embeds per-request data via `{{ data.field }}`; system prompt defines the static role/contract. The system prompt's static-ness is what enables Bedrock prefix caching via `cachePoint`.
  - **Source:** `prompt_risk/uc/uc1/p1_extraction_runner.py:88-103` (docstring)

- **Q-011** [tag: convention] [difficulty: easy]
  - **Q:** What does the `data` namespace mean in `{{ data.narrative }}`?
  - **A:** It enforces a single-object-in pattern — the user-prompt template receives exactly one `data` parameter, a Pydantic model instance. Prevents collisions with Jinja built-ins.
  - **Source:** `_references/interview-qa.md#Q21`, `prompt_risk/uc/uc1/p1_extraction_runner.py:121`

- **Q-012** [tag: arch] [difficulty: easy]
  - **Q:** What three assertion operators does `evaluate()` support?
  - **A:** `eq` (scalar `==`), `in` (list membership for "any-of" cases), `ne` (negative — output must NOT match attacker-injected value).
  - **Source:** `prompt_risk/evaluations.py:45-101`

- **Q-013** [tag: knowhow] [difficulty: medium]
  - **Q:** Why is evaluation AND logic instead of weighted/partial-credit scoring?
  - **A:** It serves a binary decision: did the prompt hold up against this input? Partial credit obscures signal. Granularity is preserved in `EvalResult.details` for inspection.
  - **Source:** `_references/interview-qa.md#Q33`

- **Q-014** [tag: arch] [difficulty: medium]
  - **Q:** In a TOML test case, which sections drive `eq`/`in` versus `ne` assertions?
  - **A:** `[expected]` drives `eq` (scalar) and `in` (list); `[attack_target]` drives `ne`.
  - **Source:** `prompt_risk/evaluations.py:71-96`, `data/uc1-claim-intake/prompts/p1-extraction/attack/a-01-injection-in-narrative.toml`

- **Q-015** [tag: knowhow] [difficulty: hard]
  - **Q:** Can a single test case have both `[expected]` and `[attack_target]` sections? Why?
  - **A:** Yes — `a-01-injection-in-narrative.toml` does. Tests both that the prompt resists injection AND that it still extracts the legitimate parts of the narrative correctly. Both must pass.

- **Q-016** [tag: knowhow] [difficulty: medium]
  - **Q:** What is `MAX_RETRIES = 3` and why exactly 3?
  - **A:** The max number of `converse()` calls per runner invocation. Informed heuristic: most fixable errors resolve on the 2nd try; 3rd guards edge cases without runaway API spend (cost grows linearly with retries because context accumulates).
  - **Source:** `prompt_risk/uc/uc1/p1_extraction_runner.py:68-79`

- **Q-017** [tag: knowhow] [difficulty: hard]
  - **Q:** Why is the retry pattern "feed the error back" instead of "retry from scratch"?
  - **A:** Multi-turn self-correction — the LLM sees its previous failed reply + the Pydantic validation error and can correct course. Blind retry would just re-roll the dice with the same probability of failure.
  - **Source:** `prompt_risk/uc/uc1/p1_extraction_runner.py:105-142`

- **Q-018** [tag: arch] [difficulty: medium]
  - **Q:** Where does `extract_json()` look for the JSON payload?
  - **A:** First tries to match a fenced code block (` ```json ... ``` ` or ` ``` ... ``` `) — only the **first** fence. If no fence, treats the entire response text as JSON.
  - **Source:** `prompt_risk/llm_output.py:17-53`

- **Q-019** [tag: knowhow] [difficulty: medium]
  - **Q:** Why does `extract_json()` only parse the first fenced block?
  - **A:** Prompts are designed to produce exactly one JSON object. If the LLM emits multiple, it's already violating the contract; parsing the first is the most reasonable heuristic and Pydantic + retry will catch a bad choice.
  - **Source:** `prompt_risk/llm_output.py:26-28` (docstring), `_references/interview-qa.md#Q27`

- **Q-020** [tag: arch] [difficulty: easy]

  - **A:** The full unparsed LLM text — preserved on extraction failure for downstream debugging. The original `json.JSONDecodeError` is on `.__cause__`.
  - **Source:** `prompt_risk/exc.py:8`, `prompt_risk/llm_output.py:53`

- **Q-066** [tag: knowhow] [difficulty: hard]

  - **A:** Gate 1 (authoring), Gate 2 (pre-deployment security review), Gate 3 (continuous monitoring), Gate 4 (decommission). This library powers Gate 2 fully (evaluation + judges) and partially Gate 3 (the same primitives apply to production output, with orchestration to be built).

- **Q-067** [tag: arch] [difficulty: medium]
  - **Q:** What's the 3-layer judge architecture described in the judge catalog?
  - **A:** Layer 1: rule engine (regex / keyword blocklist — cheap high-confidence patterns; not yet implemented). Layer 2: 5 LLM judges in parallel (J1–J5 — J1 implemented). Layer 3: meta-judge (aggregates Layer 2 — not yet implemented).
  - **Source:** `docs/source/03-Judge-Catalog/index.rst`, `_references/interview-qa.md#Q40`

- **Q-068** [tag: knowhow] [difficulty: hard]
  - **Q:** Why are J1 and the business-correctness judge kept separate instead of one mega-judge?
  - **A:** Separation enables a 2x2 diagnostic matrix (Business OK + Security OK / Business BAD + Security BAD / two mixed). Mixing concerns forces the judge to speculate ("this value appears to be influenced by injection") rather than objectively assessing factual accuracy.
  - **Source:** `data/uc1-claim-intake/prompts/p1-extraction-judge/versions/01/metadata.toml` (comments)
