# 03 — Elevation Roadmap

If you had 3–6 more months on this project, where would you invest? This doc lists the highest-leverage upgrades, the alternatives that were considered (or worth considering), and the **prerequisite knowledge** the inheritor would need to do each one well.

Framing: this is **not** "the project is bad because…" — it's "the next maturity level looks like…". Most items are written in the author's voice from `_references/interview-qa.md` (especially Category 10) and `_references/author-design-notes.md` ("What's not yet built" section).

## Executive view — top 5 highest-leverage upgrades, in priority order

1. **Automated end-to-end evaluation pipeline (Agent-driven orchestration).** Iterate all prompt versions × all test cases × all judges; produce a consolidated risk report. Currently every full evaluation requires hand-edits to example scripts. This turns the library from a manual tool into a CI-integratable scanner. (Author's own #1 pick — Q88.)
2. **Implement J4 Instruction Conflict judge.** Would catch v04 (the design-by-committee anti-pattern) automatically. Highest-leverage *new* judge to build because J1 demonstrably misses instruction conflicts (Q42).
3. **Externalize model + AWS profile to configuration.** Today `model_id` defaults are hardcoded per runner and the AWS profile name is hardcoded to `yuan_yingqiang_dev`. Production-readiness requires both to come from env vars / config files, with IAM role assumption as the deployment story.
4. **Implement P4 (Coverage Check) and P5 (Routing).** The chain is incomplete — UC1 demonstrates P1→P3 but the published mental model is P1→P5. P4 needs policy-rule data; P5 is a small extension on top of P4. Unblocks "complete pipeline" claims in demos and proposals.
5. **Integrate judge results into the evaluation engine (`PromptVersionReport`).** Today assertion results and judge results are produced separately by separate scripts. A unified per-version report ("did this version pass functional correctness AND structural security?") is the natural output Gate 2 reviewers will demand.

## Upgrade areas

### Observability and ops readiness

**Current state.** No structured logging. Runners and judges `print()` directly to stdout (`prompt_risk/uc/uc1/p1_extraction_runner.py` and similar). No metrics — token counts, retry counts, cache-hit rates, judge inter-rater variance are all invisible.

**Senior-engineer target state.** Each LLM call emits a structured log record (JSON) with: prompt ID + version, model ID, attempt number, input/output token counts, latency, cache hit/miss, validation pass/fail. CloudWatch dashboards for cache-hit rate (proxy for cost), retry distribution (proxy for prompt quality), and per-prompt-version success rate. A small `metrics.py` module that wraps `converse()`.

**Alternatives.**
- **(A) Plain `logging.getLogger(__name__)` with JSON formatter.** Lightweight, no deps. Drop-in for `print()`. Cheap to add. Trade-off: limited downstream — you can grep but not aggregate.
- **(B) OpenTelemetry spans around each `converse()` call.** Standard, supports propagation across the planned Agent SDK orchestration. Trade-off: heavier dep, requires a collector.
- **(C) AWS Bedrock model-invocation logging** (already available — turn on at AWS account level). Captures everything Bedrock sees with zero code changes. Trade-off: AWS-vendor-locked, no application-level enrichment.

**Knowledge prerequisites.**
- Structured logging in Python (`logging.LoggerAdapter`, `python-json-logger`).
- OpenTelemetry SDK basics (tracer, span attributes, propagation).
- CloudWatch Logs Insights query syntax.
- Token-counting via the Bedrock response metadata `usage.{inputTokens,outputTokens,totalTokens}`.

**Suggested learning path.**
1. Python stdlib `logging` cookbook (the official Python docs cookbook is best).
2. `opentelemetry-python` quickstart for Python.
3. AWS Bedrock model-invocation logging configuration (CloudWatch Logs or S3).
4. Tying it together: a small `prompt_risk/observability.py` module + retrofit two runners.

### Test depth and coverage

**Current state.** Unit tests cover pure-logic modules only: `evaluations.py`, `prompts.py`, `llm_output.py`, `constants.py`, `paths.py`, `exc.py`. LLM-dependent code (runners, judges) is excluded from coverage by `.coveragerc`. Integration testing is manual — you edit `examples/run_uc1_p1_extraction.py` and run it. No CI for the integration path (cost control).

**Senior-engineer target state.** A three-tier test pyramid (author's plan, Q66):
- **Tier 1: unit** — current. Pure logic. Runs on every commit. Zero LLM cost.
- **Tier 2: nightly integration** — curated subset of test cases × prompt versions × Nova Lite. Catches regressions without per-commit spend. ~10–20 calls per nightly. Schedule via GitHub Actions cron.
- **Tier 3: weekly full matrix** — all versions × all test cases × all judges. ~100+ calls; produces the deployment-readiness report.

Plus: **golden-output snapshot tests** for the LLM-driven code paths — record one canonical output per prompt-version × test-case, diff future runs against it. Drift signals model regression or prompt drift.

**Alternatives.**
- **(A) Mock Bedrock for unit tests.** Use `botocore.stub` to make runners fully unit-testable. Trade-off: mocks drift from real Bedrock behavior; you end up testing your mock.
- **(B) Skip integration in CI entirely.** Status quo — manual + visual. Trade-off: regressions discovered late.
- **(C) Hybrid: nightly with budget gate.** Run integration in CI but cap monthly spend ($X per repo); abort tier 2 if budget exhausted.

**Knowledge prerequisites.**
- pytest fixtures and parametrize for matrix tests.
- GitHub Actions `schedule:` triggers; `secrets.AWS_ROLE_ARN` for OIDC role assumption.
- Snapshot testing (`syrupy` or custom JSON-diff).
- Statistical understanding of LLM non-determinism (when is a snapshot regression real?).

**Suggested learning path.**
1. pytest `parametrize` deep-dive (the official pytest docs).
2. GitHub Actions for AWS OIDC (`aws-actions/configure-aws-credentials@v4`).
3. `syrupy` for snapshot testing in Python.
4. Run a small calibration study: same prompt × test case × 20 runs → variance distribution.

### Security and threat model

**Current state.** Three attack types tested for UC1-P1 (`a-01` direct injection, `a-02` hidden HTML-comment instructions, `a-03` SYSTEM ADMIN role confusion). Chain-propagation attacks tested for P2/P3. J1 evaluates over-permissive authorization. **What's not tested:** prompt extraction attacks (OWASP LLM07), multi-turn injection, indirect injection via external data, jailbreaking. Authoring guidelines in the governance doc explicitly say "assume prompts will be extracted" but no test verifies extraction resistance.

**Senior-engineer target state.**
- Implement **J2 Hardcoded Sensitive Data** to scan prompts for embedded pricing rules, actuarial formulas, business logic that a user could exfiltrate.
- Implement **J3 Role Confusion** (relevant especially when UC6 customer-facing is in scope).
- Implement **J4 Instruction Conflict** (highest immediate value — would catch v04).
- Implement **J5 Logic Ambiguity** for soft qualifiers ("usually", "try to avoid", "unless necessary").
- Add **prompt extraction attack cases** to each prompt's `attack/` directory once a free-text-response use case lands (UC6 chatbot).
- Add a small **rule-based pre-filter** (Layer 1 of the three-layer judge catalog) — regex/keyword blocklist for cheap high-confidence patterns ("never refuse", "always comply").

**Alternatives.**
- **(A) Build all 5 judges incrementally.** Slow but each is a complete unit. Author's stated plan.
- **(B) Build a single "all-risks" mega-judge.** Faster to ship; one prompt, multiple criteria. Trade-off: harder to calibrate; criteria interact (J1's "AS WRITTEN" rule conflicts with judging instruction conflicts holistically).
- **(C) Adopt an external prompt-security framework** (PromptArmor, NeMo Guardrails, OpenAI Moderation). Trade-off: vendor lock-in; loses the "prompts as code" governance story.

**Knowledge prerequisites.**
- OWASP LLM Top 10 (especially LLM01 Prompt Injection, LLM06 Excessive Agency, LLM07 System Prompt Leakage).
- The author's risk taxonomy (`docs/source/01-Project-Background/01-Risk-Taxonomy/index.rst`) — 5 risk categories with examples.
- Calibration methodology: known-answer testing (Q42, Q52); inter-rater reliability (Q48).
- Adversarial prompt research (papers on jailbreaking, indirect injection).

**Suggested learning path.**
1. Read the OWASP LLM Top 10 (2025 edition) cover-to-cover.
2. `docs/source/03-Judge-Catalog/index.rst` for the planned 5 judges.
3. Replicate the J1 demo notebook (`docs/source/08-Judge-Demo/index.md`) end-to-end.
4. Build J4 following the J1 pattern (`docs/source/07-Judge-Design/index.rst` §6).

### Developer experience

**Current state.** `mise` + `uv` is already fast. Test pattern (`python tests/test_x.py` as subprocess) is well-engineered. But: AWS profile is hardcoded; `print()`-based debugging; no pre-commit hooks; no type-checker in CI (only via IDE).

**Senior-engineer target state.**
- **Pre-commit hooks** for `ruff format` + `ruff check` + `mypy --strict` (selected modules) + basic `pytest tests/test_evaluations.py` smoke.
- **`OneConfigMixin.config` populated** — read from `.env` / pyproject `[tool.prompt_risk]` / env var, with overrides. AWS profile becomes one config field.
- **`tox` or `nox` for multi-version Python testing** if 3.13/3.14 support is desired (currently 3.12 only).
- **Editable install in dev** (`uv pip install -e .` is implicit but document it).

**Alternatives.**
- **(A) pre-commit framework** (`pre-commit-hooks` package). Standard, well-understood. Trade-off: another tool to install (or `mise run pre-commit` task).
- **(B) Just rely on CI to catch formatting/lint.** Cheaper to set up. Trade-off: feedback loop is longer; PRs get noisy with "fix formatting" commits.
- **(C) `make`-style aliases via `mise.toml`.** Already partially done. Could add `mise run check` for full local quality gate.

**Knowledge prerequisites.**
- `ruff` configuration in `pyproject.toml`.
- `mypy` strict mode and stub packages.
- `pre-commit` framework hook config.
- Pydantic settings (`pydantic-settings`) for typed config loading.

**Suggested learning path.**
1. `ruff` docs (it's small — read in one sitting).
2. `mypy --strict` on `evaluations.py` first; expand outward.
3. `pre-commit` quickstart.
4. Refactor `OneConfigMixin.config` to load `pydantic_settings.BaseSettings`.

### Deployment maturity (CI/CD)

**Current state.** GitHub Actions CI runs on push (`.github/workflows/main.yml`). Codecov reports coverage. ReadTheDocs builds docs. PyPI publish via `mise run publish` requires manual trigger and `$PYPI_TOKEN`. Release is via `mise run release` (idempotent).

**Senior-engineer target state.**
- **OIDC for AWS in CI** (no long-lived `AWS_ACCESS_KEY_ID` secrets — use `aws-actions/configure-aws-credentials@v4` + a role).
- **Auto-publish on tag** — push a `v0.x.y` tag → CI runs full tier 1 + 2 → publishes wheel to PyPI + creates GitHub release.
- **Trusted-Publisher PyPI auth** (no `$PYPI_TOKEN`).
- **Pre-release channel** (`0.x.y.devN` → TestPyPI) for downstream consumer testing.
- **`uv.lock` lockfile in the wheel** so reproducible installs in downstream apps.

**Alternatives.**
- **(A) Hatch / Setuptools-build.** Already on `uv build` which uses standard build backends.
- **(B) ReleaseDrafter for changelog.** Auto-generates release notes from PRs.
- **(C) Stay manual.** Single-maintainer phase tolerates this.

**Knowledge prerequisites.**
- GitHub Actions OIDC for AWS / PyPI Trusted Publishers.
- Semantic versioning (already practiced — `pyproject.toml` mentions following semver).
- `uv build` and `uv publish` mechanics.

**Suggested learning path.**
1. PyPI's "Trusted Publishers" documentation.
2. `aws-actions/configure-aws-credentials@v4` README.
3. Walk through `mise.toml`'s `publish` + `release` tasks; identify what to lift into CI.

### Documentation and onboarding

**Current state.** Strong narrative docs at 9 Sphinx chapters + 2 jupyter demo notebooks + `INDEX.md` files + this very meta-skill output. The `_references/author-design-notes.md` and `_references/interview-qa.md` are exceptional onboarding material. Weak spot: **the demo notebooks reference live Bedrock**; readers without AWS access can't replicate them — there are no captured/cached outputs.

**Senior-engineer target state.**
- **Static demo output** — store the actual JSON from `print_j1_result()` and `print_eval_result()` runs in markdown next to the notebooks, so the docs site shows results even when not running live.
- **An API reference page** (sphinx-autosummary or sphinx-autodoc2) for the public surface (`Prompt`, `evaluate`, `run_j1_over_permissive`, `run_p1_extraction`).
- **A "first 30 minutes" tutorial** that takes a brand-new user from `mise install` to running J1 against v01 vs v02 and seeing the score difference.
- A page-per-judge planning doc (J2–J5 stubs in `03-Judge-Catalog/`) so contributors picking one up know the spec.

**Alternatives.**
- **(A) MkDocs Material instead of Sphinx.** Faster build, friendlier nav. Trade-off: throws away current Sphinx infra and ReadTheDocs setup.
- **(B) Embed `prompt-risk` demos in a Gradio / Streamlit app on HuggingFace Spaces** for zero-install discovery. Trade-off: needs a hosted API key.
- **(C) Status quo — improve incrementally.** Cheapest.

**Knowledge prerequisites.**
- Sphinx directives (`autodoc`, `autosummary`, `intersphinx`).
- nbsphinx for notebook rendering.
- Diátaxis framework (tutorial / how-to / reference / explanation).

**Suggested learning path.**
1. Diátaxis quick read (`diataxis.fr`).
2. sphinx-autosummary + autodoc tutorial.
3. Convert one example script into a tutorial page.

## Projects-not-included (hypotheses + evidence)

Things that were probably considered but not built. Listed as falsifiable claims grounded in code/doc evidence.

No `deployment_status`, `decommission_date`, `predecessor_version`. Q23 mentions these as production-governance additions. Hypothesis: deferred because the library is dev-time only and a Prompt Registry would own this metadata.
- **A complete UC2-style use case** — evidence: `data/uc1-claim-intake/` is fully populated; no `uc2-*` directory exists. `_references/author-design-notes.md` mentions reusable infrastructure (~70%) and shows the pattern, but only UC1 was built. Hypothesis: prioritized depth over breadth — one fully realized UC1 (with vulnerable variants) demonstrates the methodology better than five shallow UC2-UC6 stubs.
- **`OneConfigMixin.config` actually populated** — evidence: `prompt_risk/one/one_02_config.py` returns `None`. Q13/Q69 both reference it as the intended home for env config but it's a placeholder. Hypothesis: deferred to the moment a second developer joins.
- **Layer-1 rule engine** of the 3-layer judge architecture — evidence: `docs/source/03-Judge-Catalog/index.rst` describes a rule engine for cheap regex-based patterns (R1, R2). No `prompt_risk/rules/` module exists. Hypothesis: deferred because Layer 2 (LLM judges) is more interesting research; rules are mechanically straightforward to add later.
- **Meta-judge** (Layer 3) — evidence: same doc mentions a meta-judge that aggregates Layer 2 results. No `prompt_risk/meta_judge.py`. Hypothesis: only useful once 2–3 Layer-2 judges exist.
- **A claude-agent-sdk-driven orchestrator** — evidence: `claude-agent-sdk` is in `pyproject.toml` dependencies but **no module imports it**. Q7/Q66 confirm: it's reserved for the planned Agent-driven test runner. Hypothesis: scaffolded as a dependency before the orchestrator was written, signalling intent.
