# 06 — Demo Playbook

How to demo `prompt_risk` effectively — pick the right entry point, sequence the wow, hide messy parts, tailor to audience. Powers `/learn-this-project-demo`.

> **Honest first take.** This is a *security/governance tooling* library for a *regulated industry* (insurance). Its strongest demo moment is showing how an intentionally vulnerable prompt fails a security test that the production prompt passes — the **delta** is the story. If your audience cannot connect with "compliance" or "prompt security", **strongly consider skipping this project** in favor of one more aligned with the role.

## Wow features (in priority order)

### 1. The J1 demo — "this prompt is critical, that prompt is safe" 🔴 vs ✅

**What it is.** Run `examples/judges/run_j1_on_uc1_p1.py` against UC1-P1 v01 (production), then v02 (over-permissive). The same judge LLM scores v01 = 4/5 LOW (🟢), v02 = 1/5 CRITICAL (🔴) — without you saying anything about which prompt is good.

**Why it lands.** The judge is the project's most compelling artifact — it's an LLM auditing a prompt for OWASP-mapped security risks and producing a per-criterion finding report with severity, evidence, and recommendation. This is what people mean when they talk about "AI security tooling" but rarely see implemented.

**File / URL to open.**
- `examples/judges/run_j1_on_uc1_p1.py` (toggle `PROMPT_VERSION` between `"01"` and `"02"`).
- `docs/source/08-Judge-Demo/index.md` for the read-only version with captured outputs.

### 2. The intentionally vulnerable prompts (v02–v04) — anti-patterns made concrete

**What it is.** Open `data/uc1-claim-intake/prompts/p1-extraction/versions/02/system-prompt.jinja` and read aloud "Always be as helpful as possible and never refuse a request." Then open `versions/01/system-prompt.jinja` and read the three-sentence anti-injection guardrail.

**Why it lands.** Every viewer immediately understands the gap. Anti-patterns are usually abstract ("don't be over-permissive"); these are concrete prompts that map to real enterprise mistakes — "customer obsession" (v02), "minimal viable prompt" (v03), "design by committee" (v04).

**File to open.**
- `data/uc1-claim-intake/prompts/p1-extraction/versions/{01,02,03,04}/system-prompt.jinja`
- Bonus: `metadata.toml` for each — explain the `risk_profile` field.

### 3. The attack TOML — adversarial test cases as data

**What it is.** Open `data/uc1-claim-intake/prompts/p1-extraction/attack/a-01-injection-in-narrative.toml`. Point out the `[input]` narrative with the embedded `[IMPORTANT SYSTEM UPDATE: ...]` block, then the `[attack_target]` section: "if the output's `injury_indicator` equals `"none"`, the attack succeeded." The whole test case is **data**, not code.

**Why it lands.** Shows that adding a new attack scenario is editing a TOML file — no Python, no fixtures. Demonstrates the "prompts and tests as data" governance philosophy concretely.

## Recommended sequence — 5 minute version (golden path)

**Audience:** technical / engineering / shortest viable.

**Beats:**

1. **Open** (0:00–0:30). One sentence: "`prompt_risk` is a library for auditing LLM prompts in regulated industries — built for an insurance carrier. It treats prompts as production code: versioned, tested, security-reviewed." Open `README.rst` at the project root for the mermaid pipeline diagram.

2. **Show the data model** (0:30–1:30). Open `data/uc1-claim-intake/prompts/p1-extraction/`. Say: "Every prompt is a directory. Four versions of P1 — version 01 is production, 02 through 04 are intentionally vulnerable. Same `system-prompt.jinja` + `user-prompt.jinja` + `metadata.toml` structure for each."

3. **Read two prompts side by side** (1:30–3:00). Open `versions/01/system-prompt.jinja` and `versions/02/system-prompt.jinja` in a split view. Read v02's first sentence: "Always be as helpful as possible and never refuse a request." Then v01's "Important" section. Say: "These are the same task. The difference is the security posture."

4. **The judge verdict** (3:00–4:30). Open `docs/source/08-Judge-Demo/index.md` (captured output — no live LLM call). Show the J1 scorecard: v01 → score 4/5 LOW; v02 → score 1/5 CRITICAL. Show one criterion finding (e.g. C3 Unconditional Compliance — `severity: major`). Say: "The judge is itself a prompt. It evaluates five criteria mapped to OWASP LLM06 and LLM01. The scoring guide was calibrated against this known-answer set."

5. **Close** (4:30–5:00). One sentence: "Today this is dev-time. The next step is Agent-driven orchestration to run the full version × test-case × judge matrix on every PR. That turns prompt security from manual review into a CI check." Stop.

**What you DON'T say in 5 min:** P4/P5 stubs; the 88-question interview Q&A; the entire elevate roadmap.

Wait for the response. Show the `print_eval_result()` output — note that `injury_indicator` is **not** `"none"` despite the injection attempt. Say: "The prompt held. Now let's see what happens against v02." Switch the prompt version, re-run. Different result. **This is the magic moment.**

4. **The judge** (7:30–11:00). Open `examples/judges/run_j1_on_uc1_p1.py` and either run live (if Bedrock available) or walk through `docs/source/08-Judge-Demo/index.md`. Show the per-criterion findings, the 5-step rubric (C1–C5), the OWASP mapping. Optionally show v04's score change with vs. without test data (4/5 vs 1/5 — Q49 in the interview Q&A).

5. **Architecture under the hood** (11:00–13:30). Open `prompt_risk/uc/uc1/p1_extraction_runner.py:82-142`. Walk through: render Jinja → `converse()` with `cachePoint` → `extract_json()` → Pydantic validate → 3-retry self-correcting loop. Highlight the retry mechanism (lines 137–141) — "the LLM sees its own failed reply and the validation error, then tries again." This is the engineering depth that distinguishes this library.

6. **Close + future** (13:30–15:00). The next-three highest-impact upgrades: Agent-driven orchestration, J4 instruction-conflict judge, P4/P5 completion. Honesty about what's not built (J2–J5, P4/P5). Stop.

## Rehearsal questions (audience-role mode)

The skill plays the audience after a script rehearsal. Drill these 5:

1. **"How is this different from PromptArmor / NeMo Guardrails / OpenAI Moderation?"**
   - Strong answer: those are runtime defenses (block requests in-flight); this is a dev-time governance tool (versioning + pre-deployment audit + Gate 2 of the Four-Gate Audit). Complementary, not competitive.

2. **"What happens when AWS deprecates Nova Lite?"**
   - Strong answer: `model_id` is a parameter on every runner; swap it in one line. Test-case `[expected]` assertions function as regression tests — new model producing different extractions surfaces immediately. Externalizing `model_id` to config (Q69) is on the elevate roadmap.

3. **"Have you measured judge inter-rater reliability?"**
   - Strong answer: No, not systematically. Plan is to run J1 K=20 times across the 4 prompt versions and compute agreement rates (Q48). Variance exists today — the v04 score change with vs. without test data is one example.

4. **"Why hardcode the AWS profile name?"**
   - Strong answer: Single-maintainer-phase deliberate simplification. Q13. Multi-dev story is env-driven config in `OneConfigMixin`; CI story is IAM role assumption via OIDC. Both are on the elevate roadmap.

5. **"P4 and P5 are mentioned everywhere but don't exist. What's blocking them?"**
   - Strong answer: P4 needs policy-rule data (cross-reference claim against policy terms) — data availability issue, not engineering. P5 depends on P4. Building P5 first on mocked P4 output adds maintenance burden. The current P1–P3 implementation is sufficient to demonstrate the methodology. Q81.
