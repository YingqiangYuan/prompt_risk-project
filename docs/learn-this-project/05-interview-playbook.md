# 05 — Interview Playbook

Production-grade questions, model answers, follow-ups, and weak-answer signatures for `/learn-this-project-interview`. **Model answers are reference only — never dumped to the candidate during the interview.**

The 10-category, 88-question deep bank is in `_references/interview-qa.md`. This file curates the highest-signal subset organized into rounds, and adds **what a weak answer looks like** + **what to push back on** for each question (the candidate-facing skill needs these to grade and probe).

## Opening — the 90-second pitch (model script ~150 words)

> "`prompt_risk` is a Python framework I'm building for an enterprise insurance carrier. The problem is that AI Agents in claims, underwriting, and customer service all rely on prompts — and prompts are code that nobody version-controls or security-reviews. Insurance is heavily regulated, so a compromised prompt isn't an inconvenience; it can cause regulatory action.
>
> The library does three things. First, **prompt versioning** — every prompt is a directory under `data/` with a `metadata.toml`, including intentionally vulnerable variants for regression testing. Second, **evaluation** — a model-agnostic engine that scores prompt output against TOML test cases using three operators: `eq`, `in`, and `ne` for attack detection. Third, **LLM-as-judge** — J1 evaluates prompt text itself across five criteria mapped to OWASP LLM06 and LLM01.
>
> It powers Gate 2 of a Four-Gate Audit Workflow — pre-deployment security review. It's a development-time tool, not on the production request path. About 1k LOC, ~80% coverage on the pure-logic modules."

**What the interviewer listens for:**
- Does the candidate emphasize WHY (insurance regulation, prompt-as-code governance) or only WHAT (Python, Bedrock)?
- Do they distinguish "evaluation" (output) from "judging" (prompt text itself)?
- Do they signal what's NOT built (P4/P5, J2–J5)?
- Do they own the v0.1.1 Beta phase honestly?

## Round 1 — What you have (mechanism, data flow, architecture)

### R1.Q1. Walk me through the data flow from a raw FNOL narrative to a final triage result.

**Model answer** (3–5 sentences): UC1 is a three-step chain implemented (P1→P2→P3) with P4/P5 planned. Narrative enters P1 Extraction — validated as `P1ExtractionUserPromptData`, rendered into Jinja, sent to Bedrock with cached system prompt, output parsed into `P1ExtractionOutput`. P1's JSON output passes to P2 Classification (`{{ data.extraction_json }}` in the template) which returns line-of-business + confidence. P3 Triage receives **both** extraction and classification JSON to assign severity 1–5 and priority. Every step is: load versioned prompt → render → `converse()` → `extract_json()` → Pydantic validate → up to 3 retries with self-correcting feedback. (Source: `_references/interview-qa.md#Q8`.)

**Follow-ups to press with.**
- "If P1 gets injected, what protects P2?" → expect: Pydantic re-validates structural fields; free-text fields propagate; that's why P2 has its own anti-injection guardrails and its own attack test cases.
- "Why JSON string between steps, not Python objects?" → expect: Jinja embeds directly; models realistic deployment; preserves attack payloads for testing.

**Weak answer signature.** "It calls the LLM and returns the result" with no mention of validation, retry, or chain propagation. Or: confusing the security judge (J1) with the business-correctness judge (extraction-judge).

### R1.Q2. What is `PromptIdEnum` and why does it look the way it does?

**Model answer.** A `StrEnum` whose values are `{use_case_id}:{short_name}` like `"uc1-claim-intake:p1-extraction"`. Computed props `use_case_id`, `short_name`, `dir_root` derive everything. The colon-delimited string serves as both programmatic ID and human-readable label — print/log/dict-key without serialization (standard convention: Docker images, Maven, Kubernetes). The enum ensures only registered combinations are valid at the type level. (Q10.)

**Follow-ups.**
- "Why not a tuple `(use_case, step)`?" → adds ceremony without benefit; loses the print/log/key advantage.
- "How does it relate to `dir_root`?" → `dir_root` joins `path_enum.dir_data` with `use_case_id` and `"prompts"` and `short_name` — type-safe path resolution.

**Weak answer signature.** Treats it as a passive constant list with no design rationale.

---

### R1.Q3. Explain the self-correcting retry pattern. Why isn't it abstracted into a shared helper?

**Model answer.** Each runner / judge has its own 3-attempt loop. On `ValidationError`, append the assistant's failed reply + a user message with the validation error, then retry. The LLM sees what it produced and why it failed — multi-turn self-correction, not blind retry. Most errors resolve on attempt 2; attempt 3 guards edge cases. The loop is ~8 lines and duplicated intentionally — abstracting would add indirection without reducing complexity, and each module stays self-contained and readable. (Q17, Q29, Q46, Q60.)

**Follow-ups.**
- "Why exactly 3?" → token economics — each attempt accumulates the full conversation history (3x tokens by attempt 3), and a 4th would be 4x with diminishing returns.
- "When would you abstract?" → when adding observability (logging per attempt) — at that point the duplication crosses the cost threshold.

**Weak answer signature.** "It retries 3 times" — no mention of feeding the error back, no token-economics reasoning, no defense of the duplication.

### R1.Q4. How does the evaluation engine work, and why exactly those three operators?

**Model answer.** `evaluate(output, expected, attack_target)` returns an `EvalResult`. Operators: `eq` (scalar `==` on `[expected]` fields), `in` (list membership — "any-of"), `ne` (negative — `[attack_target]` fields must NOT match injected values). AND logic — all must pass. Three operators match the three assertion types that actually arise; Pydantic already enforces structural validity before `evaluate()` runs, so regex/range checks are unnecessary. Binary decision serves the question "did the prompt hold up?"; per-field detail is preserved in `EvalResult.details`. (Q32, Q33, Q34.)

**Follow-ups.**
- "Why not weighted scoring?" → that's the judge system's job (1–5 score); evaluation is binary per test case for actionability.
- "What if the LLM omits a field?" → can't happen; Pydantic catches it before `evaluate()` runs.

**Weak answer signature.** Doesn't distinguish evaluation (output testing) from judging (prompt-text auditing).

---

### R1.Q5. Why is the judge framework layer's input plain strings, not `Prompt` objects?

**Model answer.** Zero coupling. The framework layer can evaluate prompts from any source — DB, API, clipboard, CI artifact — without going through `PromptIdEnum` and the `Prompt` dataclass. The binding layer (e.g., `run_j1_on_uc1_p1()`) handles use-case-specific loading and assembles `J1UserPromptData` with plain strings. (Q50.) This separation enables both axes of independent extensibility: new use case = new binding only; new judge = new framework function only.

**Follow-ups.**
- "What does a binding layer's responsibilities look like?" → load `PromptIdEnum`, optionally render user prompt with test data via loader, build `J1UserPromptData`, call framework.
- "Would you ever pass a `Prompt` object?" → would couple to the project's prompt management; loses portability. Worth the small redundancy.

**Weak answer signature.** Doesn't explain the two-layer extensibility benefit — describes it as just a stylistic choice.

---

### R1.Q6. Walk me through how Bedrock prompt caching works in this codebase.

**Model answer.** System prompt is sent as `[{"text": system_prompt}, {"cachePoint": {"type": "default"}}]`. Bedrock caches everything before the marker. Cache key = hash(prefix + model ID); TTL ~5 minutes; cache hits get ~90% discount on cached tokens. User prompt is **excluded** from caching because it changes every request — caching it would pay cache-write cost with zero hit chance. The system prompt's static-ness is what makes this work; this is one of three reasons (alongside contract clarity and Converse API mapping) for separating system + user files. (Q30, Q31, Q54, Q75.)

**Follow-ups.**
- "What about within the 3-retry loop?" → attempts 2 and 3 use the same system prompt → cache hits — meaningful cost savings on failed-retry paths.
- "Could you cache the user prompt template (not the rendered one)?" → no; Bedrock caches what gets sent in `converse()`, which is the rendered text.

**Weak answer signature.** Conflates the Jinja template with the rendered text; can't articulate why caching the user prompt is a net loss.

## Round 2 — What you'd elevate (3–6 month investments)

### R2.Q1. If you had 3–6 more months, what would you build first?

**Model answer.** Automated end-to-end evaluation pipeline. Today every full evaluation needs hand-edits to example scripts. An Agent-driven test runner that iterates all prompt versions × all test cases × all judges → consolidated risk report turns this from a manual tool into a CI-integratable scanner. The `claude-agent-sdk` dep is already in `pyproject.toml` for this purpose. With it: "which versions are safe to deploy?" in one command; Gate 2 reports automatically generated; regressions caught on prompt modifications. (Q88.)

**Follow-ups.**
- "Why orchestration before J4 (Instruction Conflict)?" → even a perfect new judge requires manual invocation without orchestration. Lift the multiplier first.
- "Cost model?" → tier 2 nightly on Nova Lite is fractions of a cent per call; full matrix is ~100 calls per release — totally manageable.

**Weak answer signature.** Generic "more tests" or "more docs" without naming the orchestration gap.

---

### R2.Q2. What's missing in observability today, and what's the senior-engineer target?

**Model answer.** Today: `print()` to stdout from runners and judges. No structured logs, no metrics — token counts, retry counts, cache-hit rates, judge inter-rater variance are all invisible. Target: each LLM call emits a JSON log record with prompt ID + version, model ID, attempt, input/output tokens, latency, cache hit/miss, pass/fail. Layer on OpenTelemetry spans for cross-call orchestration when the Agent SDK runner lands. CloudWatch dashboards for cache-hit rate (cost proxy), retry distribution (prompt-quality proxy). Alternative: AWS Bedrock model-invocation logging at the account level — zero code change, less application-level enrichment. (See `03-elevation-roadmap.md#observability-and-ops-readiness`.)

**Follow-ups.**
- "How would you measure judge inter-rater reliability?" → run J1 K times on each prompt (Q48); compute agreement on overall risk, score, per-criterion severity.
- "When to log vs. metric?" → metrics for what you want to alert on (cache-hit rate drop, retry rate spike); logs for what you want to inspect after-the-fact.

**Weak answer signature.** "Add logging" with no specifics on what to record or how to use the data.

### R2.Q3. Walk me through how you'd implement J4 (Instruction Conflict).

**Model answer.** Follow the J1 pattern. (1) Create `data/judges/prompts/j4-instruction-conflict/versions/01/` with `system-prompt.jinja` (criteria for detecting contradictory instruction pairs), `user-prompt.jinja`, `metadata.toml`. (2) Register `JUDGE_J4_INSTRUCTION_CONFLICT` in `PromptIdEnum`. (3) Create `prompt_risk/judges/j4_instruction_conflict.py` with `J4UserPromptData`, `J4Result`, `run_j4_instruction_conflict()`. (4) Add binding `prompt_risk/uc/uc1/j4_uc1_p1.py`. The key challenge is decomposing a prompt into "constraint units" and finding pairs that contradict under specific triggering conditions — v04's empathy-override is the canonical example. J4 would catch v04 automatically; J1 misses it because J1 evaluates criteria in isolation. (Q47, Q56.)

**Follow-ups.**
- "What's the calibration test suite?" → run against v04 (expect high-conflict finding) + v01–v03 (expect no major conflict). Iterate scoring guide until output matches.
- "Why is it more complex than J1?" → J4 needs to reason across the whole prompt holistically, while J1 walks criteria one at a time.

**Weak answer signature.** Re-describes J1 with renamed criteria — misses the holistic-reasoning challenge unique to J4.

### R2.Q4. What does the alternative look like for extracting the project to a multi-developer setup?

**Model answer.** Two parts. (1) **AWS auth.** Today `profile_name="yuan_yingqiang_dev"` is hardcoded — replace with environment-driven config in `OneConfigMixin` (currently `None`). For CI, IAM role assumption via OIDC (no long-lived secrets). For local devs, support env vars or a `.env` file via `pydantic-settings`. (2) **Model selection.** `model_id` is defaulted per-runner; production should externalize to config. Each runner category (extraction / classification / judge) can pick its own model — author's recommended split: Nova Lite for extraction (high-volume, cheap), Claude Sonnet/Opus for judges (need semantic reasoning). (Q13, Q69, Q76.)

**Follow-ups.**
- "Why is `OneConfigMixin.config` currently `None`?" → placeholder for the single-maintainer phase; intentional deferral, not an oversight.
- "What's the smallest change to ship this?" → swap the boto session profile from a literal to `os.environ.get('AWS_PROFILE', 'yuan_yingqiang_dev')`. One line, backward-compatible.

**Weak answer signature.** Recommends abstracting too much too early; misses the "smallest viable change" path.

## Round 3 — Alternatives considered ("Why not X?")

### R3.Q1. Why Pydantic over Python `Enum` for LLM output types — and why TOML for test cases over YAML or JSON?

**Model answer.** Pydantic + `T.Literal` (not `Enum`) because the LLM produces plain strings; `T.Literal` validates membership directly with zero transformation. `Enum` would add parse/serialize ceremony with no benefit. (Q25.) TOML over YAML/JSON because: multi-line strings via `"""..."""` (needed for 10–20-line FNOL narratives — YAML's indentation is fragile, JSON doesn't support it); `tomllib` stdlib parser since Python 3.11 (zero deps, unlike PyYAML); section headers map to test-case logical structure cleanly. (Q38.)

**Follow-ups.**
- "What if a Pydantic model field needs to feed an LLM as an enum option list?" → still use `T.Literal`, but render the literal's args into the prompt explicitly via Jinja.
- "Would you switch to JSON if tooling demanded it?" → only if multi-line was no longer a concern (e.g., separating narratives into their own files), and even then TOML has no downside.

**Weak answer signature.** Doesn't articulate the LLM-output mapping rationale for `T.Literal` — treats it as just a stylistic preference.

---

### R3.Q2. Why mixins for `One` instead of dependency injection?

**Model answer.** This is a dev/research tool, not a production service. Small dep surface (config + Bedrock client). Unit tests don't call LLMs. No runtime-swap requirement. Mixins give incremental composition — new dep = new mixin, no constructor changes. DI's value (testability, runtime swap, lifecycle management) doesn't apply at this scale. Author would switch to DI if this grew into a production service. (Q12.)

**Follow-ups.**
- "What does a real DI rewrite look like?" → constructor params per dep, factory functions, possibly `dependency-injector` package. Each runner takes a `BedrockRuntimeClient` param instead of importing `one`.
- "Does the hardcoded profile contradict this?" → yes — that's exactly the kind of brittleness DI would fix. The mixin pattern is fine; the **config** layer needs work.

**Weak answer signature.** Treats DI as universally superior; doesn't pin "when is DI worth its cost" to scale signals.

---

### R3.Q3. Why AWS Bedrock instead of calling Anthropic/OpenAI directly?

**Model answer.** Three reasons critical for enterprise insurance: (1) unified multi-model access through one API (Claude, Nova, Llama, Mistral) — `model_id` swap, no SDK swap; (2) enterprise security — data stays in AWS VPC, IAM-based access, CloudTrail audit, PrivateLink — required for FNOL PII (medical, financial); (3) prompt caching, model-invocation logging, guardrails as a service — infra features that direct API would force us to build. The compliance story alone (no data exfiltration to external SaaS) makes this non-negotiable for an insurance carrier. (Q73, Q74, Q77.)

**Follow-ups.**
- "What does the Converse API give that InvokeModel doesn't?" → model-agnostic message format; switching models is `model_id` change, not body rewrite.
- "Would you abstract for multi-provider?" → low priority. Bedrock already gives Claude/Nova/Llama/Mistral through one API. (Q85.)

**Weak answer signature.** Lists Bedrock features without tying them to insurance-specific compliance constraints.

## Round 4 — Problems hit (debugging / incidents)

### R4.Q1. Walk me through a hypothetical: J1 starts scoring the same prompt differently across runs. How do you diagnose?

**Model answer.** First confirm it's real, not perceived — run K=20 trials on the same prompt × test data; compute agreement on overall risk, score, each criterion's severity. Variance distribution tells you the magnitude. Causes to investigate, in order: (1) **temperature** — `converse()` passes none, so model default is >0; setting `temperature=0` would tighten things. (2) **prompt under-specification** — borderline severities shift when criteria definitions are wordy. The fix is concrete examples per severity (the J1 system prompt has these but could go deeper). (3) **model variance** — Nova Lite has more variance than Claude. Cross-model comparison (run J1 with both) identifies which model is the source. Mitigation for production: consensus voting across K runs, or switch to a more capable model. (Q44, Q48.)

**Follow-ups.**
- "How do you measure 'agreement'?" → kappa for ordinal scales; raw percentage agreement for borderline cases.
- "What's the cost trade-off?" → K=5 multiplies cost 5x for K-vote consensus. Use only on the deployment-readiness gate, not on every CI run.

**Weak answer signature.** Recommends "fix the prompt" without first measuring whether variance is real or anecdotal.

---

### R4.Q2. The runner consistently raises `JsonExtractionError` for one specific test case. How do you debug?

**Model answer.** The error carries `raw_output` (full LLM text) — first thing is to read it. If it's not JSON at all, the LLM has been hijacked by an injection or is refusing — check whether the input is an attack case and whether the prompt version has guardrails. If it's *almost*-JSON (trailing comma, unescaped quote), `extract_json()` falls back to parsing the whole text and `json.loads` fails — the retry loop already passes the error back; if it still fails after 3 attempts, the model is too small or the prompt is unclear about format. Try: (1) larger model via `model_id=`; (2) clearer "return JSON only" instruction at the end of the system prompt; (3) add an example to the prompt. (Q20, Q80.)

**Follow-ups.**
- "What if you can't change the prompt?" → switch to a stronger model; or post-process with a more forgiving parser like `json5`.
- "When is the format instruction at the end versus the beginning?" → end, due to recency bias in LLM attention. (Q22.)

**Weak answer signature.** "Add more retries" — misses that the loop already self-corrects; the issue is upstream.

## Round 5 — Production pushbacks

### R5.Q1. Suppose this library moves to power Gate 3 — continuous monitoring of production LLM behavior. What changes?

**Model answer.** Three signals to monitor: extraction attack attempts, role-switching attempts, refusal-rate anomalies. The library's primitives already work: `ne` operator can flag production outputs that match attack signatures (define `attack_target` dicts as monitoring patterns, run `evaluate()` on every production output). Refusal-rate tracking: log every LLM interaction, compute the ratio over time, sudden drop indicates the prompt was bypassed. Judge can run periodically against the production prompt to detect unauthorized modifications (compare version mismatch with registry). What's needed beyond the library: (a) a production integration layer that taps into the request path; (b) the prompt registry the governance doc proposes — today `data/` is a file-based registry, production needs access control, approval workflow, deployment tracking. (Q86, Q87.)

**Follow-ups.**
- "How do you avoid the monitoring becoming the bottleneck?" → run the assertion engine async on a sampled stream (1% of prod traffic), full-rate only on high-risk LoBs.
- "What does 'unauthorized modification' detection require?" → digest the active production prompt, compare to the registry-approved version, alert on mismatch. Simple cryptographic hash plus a config-time lock.

**Weak answer signature.** Rebuilds the library from scratch; misses that the existing `evaluate()` primitives already cover most of the detection logic.

---

### R5.Q2. Traffic 100x's. What breaks first?

**Model answer.** This is a dev-time library — production traffic doesn't go through it directly. But the question still applies to the **planned** orchestrator and any monitoring path. (1) Bedrock rate limits — Converse API has per-model TPS quotas. Need request batching, exponential backoff, and per-LoB priority queues. (2) Cache TTL (~5 min) — if traffic exceeds steady state, cache hit rate falls; mitigate via a hot-prefetch every 4 minutes or extending TTL via `cachePoint type`. (3) Retry storms — under load, the 3-retry pattern can amplify request volume 3x. Need a circuit breaker. (4) Cost — 100x cost growth is the actual constraint; per-LoB budget gates become essential. None of these are in the library today because they're not in the dev-time scope. (Q66.)

**Follow-ups.**
- "What changes about model selection at 100x?" → cost dominates. Even Nova Lite × 100 × N runs adds up. Differential model selection (per-runner) becomes critical.
- "Could you cache at the evaluation layer too?" → evaluation is in-memory pure logic — no caching needed.

**Weak answer signature.** Recommends generic "horizontal scale" without tying to specific Bedrock primitives (rate limits, cachePoint, model_id).

---

### R5.Q3. A regulator asks: "Which version of your prompt was deciding claims on March 15, 2026?" Can you answer?

**Model answer.** Today: partially. The `data/` directory has versioned prompts with `metadata.toml` (`description`, `date`). Git history shows when versions were added. But the library doesn't know what was **active in production** at any given time — that's the Prompt Registry's job. (Author's governance doc explicitly calls this out — Principle 4, "Single Authoritative Version".) Production-ready answer requires: (a) `metadata.toml` to gain `deployment_status` + `predecessor_version` + `decommission_date` fields (Q23); (b) every production LLM call logs the prompt ID + version actually used; (c) a registry that maps "version X was the active prompt for use case Y during date range Z". Without those, the answer is "git history says we wrote v01 on 2026-04-22 but I can't prove which version was deployed."

**Follow-ups.**
- "What's the minimum to satisfy the regulator?" → log the prompt-ID-and-version with every prod call. Cheapest possible answer; storage is cheap.
- "Why is this 'governance' and not 'engineering'?" → it's both, but the regulator cares about evidence trails, not architecture. Logs > diagrams.

**Weak answer signature.** "Git tells us" — no, git tells us what was committed; not what was deployed.

## Debrief — what to look for

After 5–8 questions, the interviewer summarizes (privately, in the skill):

- **Strengths:** does the candidate's WHY align with the author's design notes (insurance compliance, prompts-as-code, defense in depth)?
- **Weaknesses:** do they handwave on chain propagation, on the difference between J1 and the business-correctness judge, or on what's deliberately not built?
- **Senior signals:** do they volunteer tradeoffs unprompted? Do they distinguish "today" from "future"? Do they cite specific file:line when discussing mechanism?
- **Junior signals:** do they oversell ("everything is great"), confuse implementation and design rationale, or skip over the intentionally vulnerable v02–v04 (they're the most teachable moment in the whole project)?

The 3 questions to prep tighter (recommended baseline):
1. The pitch — most candidates omit the insurance-regulation framing.
2. Chain propagation — most candidates can't articulate it past P1.
3. J1 vs. extraction-judge — the naming is confusing, and confusing them in interview signals shallow reading.

For weak facts → recommend `/learn-this-project-quiz`.
For weak tradeoffs → recommend `/learn-this-project-elevate` rounds.
For weak mechanism → recommend `/learn-this-project-absorb module <name>`.
